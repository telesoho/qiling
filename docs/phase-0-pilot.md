# 阶段 0 试点规格：器灵请求识局重新解说

## 状态

**阶段 0 已确认。** 产品已确认试点为“用户通过器灵请求识局重新解说当前局面”，该无副作用操作不需要逐次确认；用户选择语音作为请求入口。本文定义试点范围，不代表语音输入、双向协议或识局 Action 已实现。

## 目标与用户价值

验证器灵是否能从“展示已连接客户端的状态”进一步成为桌面应用的统一交互入口。

首个试点只覆盖一个低风险闭环：用户明确请求器灵让识局重新解说当前棋局；识局使用当前有效分析和用户已选择的解说方式生成一段解说，再由器灵展示/朗读。它不改变棋盘、着法或引擎设置。

**用户故事：**我正在使用识局查看棋局，希望在器灵这个桌面入口发出“重新解说当前局面”的请求，由识局基于当前局面重新生成并返回解说，而不必切回识局点击“再解说一次”。

## 现状与缺口

### 已有能力

- 识局在分析结果就绪时可将解说发送给器灵；桌宠未运行时，识局侧栏仍保留解说文本。
- 识局提供“解说这一局/再解说一次”的手动操作，并基于当前棋盘、引擎候选和所选 summarizer 生成解说。
- 识局的棋灵设置包括启用状态、模板/本机 Ollama/DeepSeek 解说方式和 Ollama 模型选择。
- 器灵目前提供本机 `GET /v1/health`、`POST /v1/say` 与 `POST /v1/cancel`。`/v1/say` 是客户端向器灵送台词，不是器灵向识局发起操作的接口。

### 尚不存在的部分

- 识局没有供器灵调用的重新解说 Action 或通用客户端连接器。
- 器灵没有已定义的文字/语音意图输入与客户端能力发现机制。
- 现有接口没有定义 Action 授权、结果回传或连接生命周期。

因此，本阶段只定义产品场景与成功边界，不暗示上述能力已经存在，也不提前决定 IPC、HTTP、WebSocket 或 MCP 等实现方式。

## 目标流程

1. 识局已打开，且当前棋盘与引擎候选属于同一个有效局面。
2. 用户通过语音明确请求“重新解说当前局面”。阶段 1 提案建议按键说话和本机优先识别；触发与识别方案尚未评审实现。本规格不假定当前已有麦克风监听或语音识别能力。
3. 器灵将请求交给已连接的识局客户端。
4. 识局检查当前解说是否可用，并复用现有手动解说逻辑和用户配置的 summarizer。
5. 识局把成功生成的解说结果返回；器灵负责展示或朗读。识局仍可在侧栏保留最新解说。
6. 如果识局离线、当前分析过期/不可用或 summarizer 失败，器灵给出明确失败状态，不把失败说成成功。

## 范围与产品决策

### 纳入

- 单一客户端：识局。
- 单一 Action：对当前局面重新生成解说。
- 请求入口：语音；具体交互方式与识别流程由阶段 1 定义。
- 用户明确发起后执行；不因普通棋局事件自动反复触发。
- 此 Action 不改变棋盘、着法、引擎运行状态或识局设置，因此不增加逐次确认。
- 解说继续遵循识局当前已选择的模式、模型和数据处理行为；不得因经由器灵触发而切换到另一服务、扩大数据范围或绕过用户设置。
- Action 结果应区分至少：已完成、识局不可用、当前分析不可用/过期、解说失败。

### 不纳入

- 走棋、悔棋、重开、翻转棋盘、修改引擎参数等会改变状态的操作。
- 本阶段不实现持续常驻监听、自由对话、唤醒词、LLM 意图识别或实时语音会话；阶段 1 提案建议按键说话，仍待评审。
- 通用桌面控制、屏幕识别、鼠标键盘自动化、多客户端或插件市场。
- 在阶段 0 实现连接协议、授权 UI、SDK、MCP Adapter 或生产代码。

任何会改变棋局或设置的未来 Action 必须单独定义风险与授权规则；本试点的“不逐次确认”不能被推广为通用权限策略。

## 隐私与失败处理约束

- 器灵触发的解说必须使用识局已有配置与同一 summarizer 路径，不得静默切换网络/本机服务。
- 数据出本机与否继续由识局当前模式决定，并在调用前向用户保持现有可见说明；本试点不新增上传字段或数据用途。
- 不记录棋盘、FEN、着法、解说正文或任何密钥作为协议审计内容；结果追踪应使用不含敏感正文的请求标识和状态。
- 识局未连接、局面/引擎结果已过期、用户关闭棋灵，或 summarizer 无法工作时，应返回可区分的失败结果；不得朗读旧解说并让用户误以为已重新分析。
- 取消或重复请求的语义留待协议设计；若后续实现允许取消，必须避免把被取消请求显示为成功。

## 阶段 0 验收标准

- 产品规格明确记录目标用户、用户意图、触发边界、单一 Action、数据路径、失败状态和不做事项。
- 用户能区分“当前识局已支持的手动再解说”与“未来由器灵发起的请求”；文档不会把后者描述成现成功能。
- 试点 Action 的无副作用范围和不需逐次确认的决定有明确记录，且明确该决定不适用于会改变状态的操作。
- 试点成功可在后续实现阶段用端到端演示验证：请求指向当前局面，识局执行一次既有解说流程，器灵收到新结果；棋盘状态保持不变；离线/过期/失败不产生伪成功。
- 产品已确认本试点场景、无需逐次确认的范围和语音请求入口；阶段 1 需把语音触发方式作为待设计项，而非既有功能。

## 阶段 1 提案评审项

阶段 1 已形成[Spirit Protocol V1 提案](spirit-protocol-v1.md)，其中提出语音触发、STT 隐私边界、客户端配对、Action/事件与错误语义。上述实现方案仍需评审确认；现有识局 summarizer 的数据告知也须在实现新入口时保持一致。
