# 器灵开发计划

> 状态：方向建议，尚未承诺发布日期。根据器灵现有代码和 2026-11-01 的产品讨论整理；每个阶段应在验证前一阶段后再启动。

## 产品方向

器灵不只是一只可被外部程序调用的桌宠，而是**桌面应用之间的交互中间件**：

- **Spirit Runtime**：用户直接接触的角色、动画、语音、对话和设置。
- **Spirit Protocol**：连接应用的身份、能力发现、双向事件、Action 请求与授权。
- **Spirit SDK / Connector**：降低桌面应用和 AI Agent 的接入成本；MCP 作为适配器之一，而非底层协议的唯一形式。

产品价值应以“第三方应用接入一次后，能否获得稳定、安全、带有角色交互体验的桌面入口”衡量，而不是以桌宠动作或集成数量衡量。

## 当前基础

- Tauri 桌宠已有独立窗口、动画轨、气泡和设置。
- 语音优先使用本机 CosyVoice，并保留系统语音回退。
- 本机 HTTP API 已支持探活、送出台词和取消朗读；识局是首个客户端。
- 协议定义在 `docs/openapi.yaml`，实现位于 `src-tauri/src/http.rs`。
- 当前 API 主要是“客户端 → 器灵”的单向控制，尚无通用客户端注册、能力发现、事件订阅和“器灵 → 客户端”Action 闭环。

## 分阶段路线图

### 阶段 0：收敛产品边界（已确认）

**目标：**选定一个能验证双向通信价值的真实场景，避免过早扩展为通用自动化平台。

**工作项**

- 将“桌面应用间交互中间件”定为长期方向；桌宠、动画和语音作为交互运行时。
- 以识局作为首个协议验证客户端：用户通过器灵语音请求识局重新解说当前局面。
- 定义首个场景的用户、触发条件、允许的操作、失败处理和隐私边界。
- 暂不承诺多平台、任意应用控制或完整插件市场。

**当前状态：**产品已确认试点场景、语音请求入口，以及重新解说这一无副作用操作无需逐次确认。阶段 1 已选定唤醒词与本机优先识别；唤醒词监听必须用户显式启用、仅本机检测、状态可见且可关闭。完整边界见[阶段 0 试点规格](phase-0-pilot.md)。

**验收**

- 有一个可演示的端到端场景和明确的成功条件。
- 场景中的每个 Action 都能说明调用方、权限和执行结果如何反馈。

### 阶段 1：设计 Spirit Protocol V1（已通过评审）

**目标：**在扩展当前 HTTP API 前先确定稳定、可测试的协议边界。

**工作项**

- 定义协议版本、客户端身份与注册/断开、能力声明与查询。
- 定义双向事件、Action 请求/响应、请求 ID、超时、取消及结构化错误。
- 将语音作为试点的用户入口；用户选择本机唤醒词触发与本机优先 STT，云端 STT 需显式开启。具体引擎尚未选择，功能尚未实现。
- 为能力划分只读、可逆写入和敏感操作；明确哪些操作必须请求用户确认。
- 复用现有 `/v1/health`、`/v1/say`、`/v1/cancel`，写清兼容策略与迁移边界。
- 维护现有 OpenAPI 对已实现 HTTP API 的准确描述，并为提案消息增加独立可复用 Schema 与契约样例，避免把未实现端点列为现行 API。

**当前产物：**[Spirit Protocol V1 规格](spirit-protocol-v1.md)与[消息 Schema/示例](spirit-protocol-v1.schema.json)。用户已确认 WebSocket + JSON-RPC、唤醒词、本机优先 STT、一次性配对与首次能力授权、`siju.narrate_current` 唯一免逐次确认，以及 60 秒超时和 64 KiB 消息上限。阶段 1 已完成，阶段 2 开始实现本机连接与安全基础。

**验收**

- 至少有一份协议规格，覆盖正常流程、断线、超时、取消、未知能力、拒绝授权和版本不兼容。
- 实现与文档的请求/响应结构可由自动化契约测试校验。

### 阶段 2：建立本机连接与安全基础（已验收通过）

**目标：**支持持续、双向的本机应用连接，并让能力调用遵循最小权限。

**工作项**

- 实现客户端生命周期、能力清单、连接状态和事件传递。
- 为 Action 加入授权、撤销、超时和审计信息；默认拒绝未授权的敏感操作。
- 实现 V1 WebSocket/JSON-RPC 连接、配对与客户端撤销；V1 Action 调用接入留在阶段 3。
- 检视现有本机 HTTP API 的访问控制与 CORS。当前“监听回环地址”不等于请求已认证；在引入双向控制前，定义并测试本机客户端如何获得授权。
- 明确协议服务的并发、队列和资源上限，不向外承诺尚未实现的高并发保证。

**验收结果（2026-11-01）：**用户确认两端桌面验收测试已完成且无问题。回环 WebSocket、配对审批与拒绝、授权连接、状态事件、两端重启恢复、器灵侧撤销、识局侧解除配对及失败状态均通过。识局解除配对会同步删除器灵授权；器灵撤销后识局清除失效凭证并隐藏解除配对操作。自动化测试与两端 Tauri 原生构建也通过。旧 HTTP 写请求已校验 Origin，`/v1/say` 要求 JSON。`action.invoke` 按计划留在阶段 3。

**桌面验收清单（用户确认全部通过）**

1. **通过：**一次性配对、申请能力展示和拒绝路径。
2. **通过：**批准后认证/初始化、已连接状态及 `siju.analysis.status` 事件。
3. **通过：**器灵与识局分别重启后的授权保留和自动恢复。
4. **通过：**器灵撤销会关闭活动连接、清除识局侧失效凭证并阻止重连。
5. **通过：**识局解除配对会同步撤销器灵侧授权，原令牌不再有效。
6. **通过：**错误配对码、审批拒绝、器灵离线等错误状态及旧 HTTP 写接口保护。

**阶段边界：**本阶段只验收连接、身份、能力授权、事件和生命周期；不要求执行 `siju.narrate_current`。真实语音、唤醒词与 STT 也不属于本阶段验收。

**验收**

- 未授权客户端不能调用受保护能力；用户能查看并撤销授权。
- 客户端断开、器灵重启或请求超时后，连接和待处理请求能进入定义好的状态。
- 权限拒绝和失败均有可诊断结果，不会返回伪成功。

### 阶段 3：与识局完成双向闭环

**目标：**证明协议能解决真实问题，而不只是让桌宠播放动作。

**工作项**

- 已实现识局 `siju.analysis.status` 状态事件，并在器灵设置中显示客户端连接及可解说状态。
- 已实现范围受限的 `siju.narrate_current` Action 往返；器灵仅在客户端连接且该能力获准时提供手动触发入口。
- 识局复用用户当前解说设置，只使用仍对应当前 FEN 的分析；不将 fallback、旧局面或失败结果伪装成成功。
- 成功结果由器灵展示/朗读；失败映射为稳定错误码和可诊断状态。日志记录请求 ID、Action、结果状态与耗时，不记录解说正文或棋局数据。
- 自动化覆盖成功往返、请求 ID 关联、并发重复请求拒绝、超时及迟到响应丢弃；用户已完成桌面验收并确认未发现问题。
- 本阶段的触发入口是设置页手动按钮，不是语音入口；唤醒词与 STT 尚未实现。

**验收结果（2026-11-01）：**用户完成双端桌面验收并确认未发现问题。器灵端触发后，识局使用当前解说设置重新解说并成功回传，器灵正常结束请求状态并反馈结果；阶段 3 验收通过。

**桌面验收清单（用户确认完成）**

1. **通过：**器灵设置中识局显示“已连接”，且状态事件显示“可解说”。
2. **通过：**点击“请识局重新解说当前局面”后，识局成功重新解说，器灵正常结束请求并反馈结果。
3. **通过：**已按清单检查局面状态变化及可解说状态反馈，未发现问题。
4. **通过：**已按清单检查客户端连接/授权状态及失败反馈，未发现问题。
5. **通过：**已按清单检查解说器错误路径，未发现问题。
6. **通过（自动化）：**重复请求、超时及迟到响应由测试覆盖；迟到结果不会破坏后续连接状态。

**验收**

- 完整演示“识局状态事件 → 器灵反馈 → 已授权 Action → 识局执行 → 结果回传及语音/界面反馈”。
- 关键结果可关联到请求 ID，并能解释失败原因。
- 未获授权、客户端离线、当前状态不可用/过期、解说服务失败、重复请求或超时，均不得误报成功；迟到结果不得覆盖新状态。
- 用户已完成双端桌面验收并确认无问题；阶段 3 通过。

### 阶段 4：发布最小 SDK / Connector

**目标：**让第三方开发者不必手写连接管理和协议细节。

**工作项**

- 已选 TypeScript/Node.js 22+ 作为首个 SDK 形态；使用内置 WebSocket，无运行时依赖，不同时铺开其他语言或平台。
- `sdk/typescript` 提供配对、凭证适配、认证/初始化、状态事件上报、试点 Action 响应、解除配对、超时和断线错误处理。
- 提供可运行的协议示例、最小接入代码、支持范围/错误处理/版本兼容说明；示例用于协议冒烟测试，不冒充棋局分析客户端。
- MCP Adapter 暂不纳入本阶段；只有在 SDK/协议接入验证后再评估，保持与桌面客户端协议解耦。

**当前状态：**SDK、参考示例、自动化验证及桌面连接验收均已完成；阶段 4 通过。

**验收**

- 开发者能依照文档独立运行示例客户端并完成一个事件和一个受控 Action。
- 断线、超时、授权拒绝等核心路径有 SDK 测试。
- 凭证由调用方提供的系统凭证库适配器保存；示例的进程内凭证仅用于本地演示。
- 桌面验收通过：示例客户端成功配对并连接、上报可解说状态，且 `siju.narrate_current` 请求能完成并返回结果。

### 阶段 5：验证第二个客户端，再扩展语音

**目标：**检验协议是否能跨应用复用，并形成语音交互闭环。

**工作项**

- 先选一个第二客户端（例如 IDE），复用同一协议验证能力发现、状态事件和授权 Action。
- 在客户端接入成本和权限模型得到验证后，再扩展完整语音对话能力、STT/LLM/TTS 适配与打断能力；试点所需的语音命令入口由阶段 1 明确。
- 语音触发 Action 时仍遵循同一权限策略；语音本身不构成授权。
- 根据实际接入反馈决定是否增加浏览器 Connector 或更多运行时平台。

**验收**

- 第二个客户端无需修改协议核心即可完成接入。
- 语音会话可取消/打断；Action 执行前能呈现必要的确认，结果能反馈给用户。

## V1 暂不纳入

- 通用屏幕识别、鼠标键盘控制和任意应用自动化。
- 同时支持 Windows、macOS、Linux 的完整 Connector 矩阵。
- 大规模插件市场、云端账号体系或跨设备同步。
- 将 MCP 设为唯一通信协议。
- 未经用户授权的任意客户端操作或全系统控制权。

这些方向可能有价值，但应在原生 Connector 和权限模型经过真实场景验证后再评估。

## 技术与文档约定

- 接口变更同时更新 `docs/openapi.yaml` 和 `src-tauri/src/http.rs`；双向协议应补充相应的消息 schema、示例和契约测试。
- 继续沿用现有 `npm test` 与 `cargo test --manifest-path src-tauri/Cargo.toml` 验证前端和 Rust 逻辑。
- 每一阶段结束后，根据试用结果更新范围和验收标准；不要把路线图视为固定发布日期承诺。

## 参考方向

产品讨论中提到的 OpenPets、dsh-pet、deskq、Vibe Nanny、DeskFamiliar 等项目可用于比较桌宠运行时、插件/SDK、语音与本机 IPC 的设计。它们是调研线索，不应代替对最新实现和许可的核实。器灵的差异化假设——把双向客户端能力与权限管理作为统一协议核心——需要由阶段 3 和阶段 5 的接入结果验证。
